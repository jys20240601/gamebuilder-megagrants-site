디지털트윈 인터뷰 노트목차

MQTT 쉽게 이해하기

전체 흐름은 03 전체흐름 쉽게 참고.

한 줄

MQTT는 센서처럼 작은 기기들이 데이터를 가볍고 안정적으로 주고받도록 만든 IoT용 메시지 전달 규칙이다. 보내는 쪽과 받는 쪽이 서로를 몰라도 되고, 가운데 "브로커"가 배달을 맡는다.

  • 1999년 IBM의 앤디 스탠퍼드-클라크와 알린 니퍼가 위성으로 송유관을 감시하려고 만들었다. 통신이 느리고 자주 끊기는 환경이 출발점이었다.
  • 2014년 OASIS 표준(3.1.1)이 됐고 2016년 ISO/IEC 20922가 됐다. 2019년에 5.0이 나왔다. 삼우이머션 사례 기사에서 말한 "ISO 표준 방식"이 이것이다.

누가 만들었나: 규격과 프로그램은 다르다

MQTT 자체는 프로그램이 아니라 규격(약속 문서)이다. 그 약속을 지켜 실제로 돌아가게 만든 프로그램은 여러 곳에서 따로 만들었다. 웹에 비유하면 HTTP가 규격이고, 크롬·엣지(브라우저)와 Nginx(웹 서버)가 그 규격을 구현한 프로그램인 것과 같다.

규격(약속)을 만든 곳

시기 내용
1999 IBM의 앤디 스탠퍼드-클라크와 Arcom(나중에 Eurotech)의 알린 니퍼가 위성으로 송유관 설비를 감시하려고 설계. 이름의 MQ는 IBM 메시지 제품 MQSeries에서 왔다
2010 IBM이 규격(3.1)을 로열티 없이 공개. 누구나 무료로 구현할 수 있게 됨
2014 국제 표준화 단체 OASIS가 3.1.1을 표준으로 채택
2016 ISO/IEC 20922 국제 표준이 됨
2019 MQTT 5.0 표준. 지금은 OASIS의 MQTT 기술위원회가 관리

그래서 좋은 점

  • 모두 같은 약속을 지키므로 서로 다른 회사 제품을 섞어도 통한다. 센서는 A사, 브로커는 Mosquitto, 저장기는 Python Paho, 화면은 언리얼 플러그인이어도 연결된다.
  • 특정 회사 제품에 묶이지 않는다. 수료생이 배운 것이 어느 회사 현장에서도 그대로 쓰인다.
  • 주의할 점은 버전이다. 3.1.1과 5.0이 섞여 쓰이므로 브로커와 클라이언트가 어느 버전을 지원하는지 확인한다.

어떤 약속인가: 규격 문서에 적힌 것

약속은 OASIS가 공개한 규격 문서로 되어 있다. 회사·단체 대표가 모인 기술위원회가 문안을 만들고 투표로 확정한다. 문서에는 "반드시(MUST) ~해야 한다" 식의 규칙이 번호와 함께 적혀 있다. 예를 들어 3.1.1의 첫 규칙은 "연결 후 클라이언트가 보내는 첫 메시지는 반드시 CONNECT여야 한다 [MQTT-3.1.0-1]"이다. 프로그램을 만드는 사람은 이 규칙을 지켜 구현하고, 규칙을 지킨 프로그램끼리는 서로 통한다.

약속 내용
① 메시지 종류 3.1.1 기준 14가지(5.0은 인증용 AUTH를 더해 15가지). 접속 CONNECT·CONNACK, 보내기 PUBLISH·PUBACK(QoS 2는 PUBREC·PUBREL·PUBCOMP), 구독 SUBSCRIBE·SUBACK, 구독 해제 UNSUBSCRIBE·UNSUBACK, 안부 PINGREQ·PINGRESP, 종료 DISCONNECT
② 대화 순서 접속 → 허락 → 구독 → 확인 → 보내기 → (QoS 1이면) 수신 확인 → 안부
③ 바이트 배치 메시지마다 몇 번째 바이트에 무엇을 적는지. 첫 바이트의 앞 4비트는 종류, 뒤 4비트는 옵션(재전송 표시, QoS, Retained). 그다음 남은 길이, 토픽 길이, 토픽, 편지 번호(QoS 1·2), 내용물
④ 토픽 규칙 /로 단계 구분, UTF-8 글자, 구독할 때만 +·# 사용, $로 시작하는 토픽은 브로커 내부용
⑤ 행동 규칙 새 구독자에게 Retained 값을 보낸다, 안부 간격의 1.5배 동안 소식이 없으면 연결을 끊는다, 비정상 종료 시 유언 메시지를 발행한다, QoS는 보내는 쪽과 받는 쪽 중 낮은 쪽을 따른다
정하지 않은 것 내용물 형식(JSON 등), 토픽 이름 짓는 법, 데이터 저장, 암호화(TLS에 맡김). 이것은 프로젝트에서 따로 약속해야 한다

실제 바이트 예

토픽 busan/terminal/pump03/temp, 내용물 42.5, QoS 1, Retained를 3.1.1로 보내면 36바이트다.

33        첫 바이트: 0011(종류 3 = PUBLISH) 0(재전송 아님) 01(QoS 1) 1(Retained)
22        남은 길이 34
00 1A     토픽 길이 26
62 75 ... 토픽 "busan/terminal/pump03/temp" (26바이트)
00 01     편지 번호 1 (QoS 1·2만)
34 32 2E 35  내용물 "42.5"

같은 값을 최소한의 HTTP 요청으로 보내면 114바이트이고, 실제 브라우저나 라이브러리는 헤더가 더 붙는다. MQTT가 가볍다는 말은 이 차이를 뜻한다.

MQTT와 JSON은 다르다

  • MQTT는 배달 방법(통신 규칙)이고, JSON은 편지 쓰는 형식(표기 방식)이다.
  • MQTT 메시지 하나는 봉투(토픽, QoS, Retained)와 내용물(payload)로 되어 있다. 내용물은 JSON, 숫자 하나, CSV, 바이너리 무엇이든 된다.
  • 실무에서는 대부분 내용물을 JSON으로 쓴다. 예: 토픽 busan/terminal/pump03/temp, 내용물 {"device":"pump03","value":42.5,"unit":"C","time":"2026-11-15T10:00:00+09:00"}
  • 웹(HTTP)도 JSON을 나르고 MQTT도 JSON을 나른다. JSON은 둘 다에 실리는 내용물 형식이다.

우체국 비유

MQTT 용어 우체국 비유 디지털트윈 예
발행자(Publisher) 편지를 보내는 사람 크레인 GPS, 온도 센서
브로커(Broker) 우체국 Mosquitto, EMQX 같은 서버
토픽(Topic) 받는 주소 busan/terminal/crane07/position
구독자(Subscriber) 그 주소의 편지를 받겠다고 신청한 사람 언리얼, Python 저장 프로그램, 관제 앱
메시지(Payload) 편지 내용 {"lat":35.10,"lon":129.08,"t":"2026-11-15T10:00:00Z"} 
 크레인 GPS ──발행──▶            ──전달──▶ 언리얼 (화면에 표시)
 온도 센서 ──발행──▶   브로커     ──전달──▶ Python (정제·DB 저장)
 헬멧      ──발행──▶            ──전달──▶ 알람 앱

센서는 누가 받는지 모르고 브로커에만 보낸다. 그래서 받는 쪽을 늘리거나 바꿔도 센서는 손댈 필요가 없다.

HTTP와 무엇이 다른가

실시간 값 받기 계속 "새 값 있어?" 하고 물어야 함 연결을 유지한 채 바로 받음

일반 통신 예시

예 방식
웹 브라우저로 페이지 열기 브라우저가 서버에 요청 → 서버가 페이지를 응답 (HTTP)
앱·프로그램이 날씨 API 조회 "부산 지금 풍속?" 요청 → {"wind": 7.2} 응답 (HTTP REST API, 내용물은 JSON)

공통점: 받는 쪽이 먼저 묻고, 상대 주소를 직접 알아야 하고, 1:1이다. 비유하면 전화 걸기다. MQTT는 구독 알림에 가깝다(구독해 두면 새 소식이 알아서 오고, 보내는 쪽은 누가 받는지 모른다).

센서 하나를 세 곳(언리얼, 저장기, 알람)이 1초마다 HTTP로 물으면 센서는 1초에 3번 답해야 하고, 값이 그대로여도 계속 묻는다. MQTT는 센서가 한 번 보내면 브로커가 세 곳에 나눠 준다. 받는 곳이 100곳으로 늘어도 센서가 보내는 횟수는 같다.

디지털트윈은 둘 다 쓴다

용도 방식
실시간 상태(위치, 온도), 알람, 제어 명령 MQTT
이력 조회("어제 하루 온도"), 설정 변경, 3D 모델·문서 받기, 외부 공공 API HTTP(REST)

MQTT가 더 좋은 게 아니라 쓰임이 다르다.

꼭 알아야 할 기능 5가지

  1. 토픽 계층과 와일드카드 - 토픽은 /로 나뉜 폴더 구조다. 예: busan/terminal/crane07/position - +는 한 단계를 대신한다. busan/terminal/+/position은 모든 크레인의 위치다. - #은 그 아래 전부를 뜻한다. busan/terminal/#은 터미널의 모든 데이터다. - 토픽 설계가 곧 디지털트윈의 데이터 지도다. 앞에서 말한 "대상 정합(ID 매핑)"과 바로 이어진다.
  2. QoS (배달 보장 수준)
QoS 비유 디지털트윈에서
0 일반 우편: 보내고 끝, 잃어버릴 수 있음 1초 5회 오는 위치값. 곧 다음 값이 온다
1 등기: 최소 한 번 도착, 중복 가능 알람, 상태 변경
2 정확히 한 번 도착 (가장 느림) 제어 명령처럼 두 번 실행되면 안 되는 것
3. Retained (마지막 값 보관): 브로커가 토픽의 마지막 메시지를 기억한다. 언리얼을 새로 켜도 다음 값을 기다리지 않고 바로 현재 상태를 그린다.
4. Last Will (유언 메시지): 센서가 접속할 때 "내가 갑자기 끊기면 이걸 보내 줘"라고 맡겨 둔다. 연결이 끊기면 브로커가 대신 offline을 알린다. 트윈은 그 장비를 회색으로 바꾼다.
5. Keep Alive: 일정 간격으로 "살아 있음" 신호를 주고받아 끊김을 빨리 알아챈다.

기술 기본값

  • TCP 위에서 동작한다. 기본 포트는 1883, 암호화(TLS)는 8883이다.
  • 브로커가 WebSocket을 지원하면 브라우저에서도 받을 수 있다.
  • 보안은 TLS 암호화, 아이디·비밀번호, 토픽별 접근 권한(ACL)으로 한다.
  • 대표 브로커: Mosquitto(가벼운 오픈소스, 실습용), EMQX·HiveMQ(대규모), 클라우드 IoT 서비스.
  • 언리얼: 엔진에 MQTT 플러그인이 들어 있다(UE 5.1~5.2 무렵부터 베타·실험 단계로 보고됨). 마켓 플러그인도 있고, Python으로 중계해도 된다.

한계: 빅데이터 가공이 따로 필요한 이유

  • MQTT는 배달부이지 창고가 아니다. 지나간 메시지를 쌓아 두지 않는다(Retained는 마지막 1개뿐). 이력 분석, 재생, 예측을 하려면 구독해서 DB에 저장해야 한다.
  • 내용 형식은 정해 주지 않는다. JSON 구조, 단위, 시간 표기는 프로젝트에서 따로 약속해야 한다. 이 약속을 맞추는 일이 정제·정합 작업이다.
  • 큰 영상에는 맞지 않는다. CCTV는 AI가 인식한 결과(이벤트)만 MQTT로 보낸다.
  • 브로커가 멈추면 전체가 멈춘다. 대규모 현장은 브로커를 여러 대로 묶는다(클러스터).

구축 방법

MQTT를 돌리는 데는 세 가지가 필요하다: 브로커(우체국) 1개, 보내는 쪽, 받는 쪽. 처음 띄우는 일은 쉽고, 운영 수준으로 다듬는 일(토픽 설계, 보안, 저장, 규모)이 진짜 일이다.

1단계: 브로커 띄우기 (PC 한 대, 약 30분)

  1. Mosquitto(이클립스 재단의 오픈소스 브로커)를 설치한다. Windows 설치 파일이 있고, Docker라면 eclipse-mosquitto 이미지를 쓴다.
  2. 설정 파일 mosquitto.conf에 최소 두 줄을 넣는다. listener 1883 allow_anonymous true Mosquitto 2.0부터는 설정이 없으면 같은 PC 안(localhost)에서만 받는다. 다른 PC(언리얼 PC, 라즈베리파이)에서 접속하려면 listener가 필요하고, 이때 익명 접속은 기본으로 막혀 있어 실습에서는 allow_anonymous true로 연다(운영에서는 4단계처럼 계정을 쓴다).
  3. 터미널 두 개로 확인한다. mosquitto_sub -h localhost -t "busan/#" -v # 받는 쪽: busan 아래 전부 구독 mosquitto_pub -h localhost -t busan/test -m "hello" # 보내는 쪽 받는 쪽 창에 busan/test hello가 찍히면 성공이다.
  4. 눈으로 보려면 MQTT Explorer(무료 GUI)를 연결한다. 토픽 나무와 값이 실시간으로 보여서 수업용으로 좋다.

2단계: 센서와 저장기 붙이기 (Python, paho-mqtt)

보내는 쪽(가짜 센서 또는 라즈베리파이 온도 센서):

import json, time, random
import paho.mqtt.client as mqtt

client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2)
client.connect("브로커 IP", 1883)
client.loop_start()
while True:
    data = {"device": "pump03", "value": round(30 + random.random() * 15, 1),
            "unit": "C", "time": time.strftime("%Y-%m-%dT%H:%M:%S+09:00")}
    client.publish("busan/terminal/pump03/temp", json.dumps(data), qos=1, retain=True)
    time.sleep(1)

받는 쪽(저장기·알람):

import json
import paho.mqtt.client as mqtt

def on_message(client, userdata, msg):
    data = json.loads(msg.payload)          # JSON 풀기
    print(msg.topic, data["value"])         # 여기서 DB에 저장
    if data["value"] > 40:                  # 기준 넘으면 알람 발행
        client.publish("busan/terminal/pump03/alarm", json.dumps({"level": "warning"}), qos=1)

client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2)
client.on_message = on_message
client.connect("브로커 IP", 1883)
client.subscribe("busan/terminal/+/temp")
client.loop_forever()

코드 없이 연결하는 도구도 있다. Node-RED(블록을 선으로 이어 MQTT → DB 연결), Telegraf(MQTT를 받아 InfluxDB에 저장).

3단계: 언리얼 연결

  • 블루프린트 흐름: 브로커 접속 → 토픽 구독(busan/terminal/#) → 메시지 도착 이벤트 → JSON 풀기 → 토픽의 장비 ID로 액터 찾기 → 위치·색·UI 갱신.

언리얼에서 MQTT를 받는 방법은 세 가지다(2026-11-15 조사).

방법 내용 상태
① 엔진 내장 MQTT 플러그인 Epic이 만든 플러그인. 플러그인 창의 IOT 분류. UE 5.1~5.2 무렵 들어옴 2026년 5.6.1 보고까지도 실험 단계. 공식 문서가 거의 비어 있음. 포럼 보고: 연결 이벤트가 안 불림(5.2~5.3), 0.5초 간격 수신 시 크래시, 클라우드 브로커 접속 오류, 5.6.1에서 30초 안에 크래시, 블루프린트에서 내용물을 바이트 배열로 바꿔야 함
② 외부 플러그인(Fab 등) Total MQTT(여러 브로커 동시 접속, BP·C++), MqttLink(QoS 0/1/2, Retained, BP·C++), MqttUtilities(오픈소스, BP), UnrealMosquitto(오픈소스) 엔진 버전(5.8) 지원 여부를 제품마다 확인해야 함
③ 중계 Python·Node-RED가 MQTT를 받아 언리얼에 넘김. 언리얼 쪽은 Remote Control API(엔진 공식 기능, HTTP 30010·WebSocket 30020 포트로 액터 속성 변경·함수 호출) 또는 WebSocket 가장 안정적. 데이터 레이어(Python)와 시각화 레이어(언리얼)를 나누는 과정 설계와도 맞음
  • 수업 권장: 처음에는 ③ 중계로 확실히 동작하게 만들고, ①은 "실험 기능은 이런 문제가 있다"를 보여 주는 비교 실습으로, ②는 검증된 것 하나를 골라 쓴다.
  • 사전미팅 질문: 삼우이머션은 언리얼 MQTT 연동을 어떻게 하는가(내장 플러그인, 외부 플러그인, 자체 C++ 플러그인, 중계 서버). Epic 스포트라이트에는 MQTT를 연동했다는 사실만 있고 방법은 없다.

4단계: 운영 수준으로

항목 할 일
토픽 설계 사이트/구역/장비/항목 규칙을 먼저 정한다. 예: busan/terminal/crane07/position
내용물 약속 JSON 필드 이름, 단위, 시간 표기(예: device, value, unit, time +09:00)를 문서로 고정
보안 계정·비밀번호(mosquitto_passwd), TLS 암호화(포트 8883), 토픽별 권한(ACL)
저장 구독자가 시계열 DB에 쌓는다. MQTT 자체는 저장하지 않는다
옛 설비 Modbus·OPC UA 장비는 게이트웨이(엣지 서버)가 읽어서 MQTT로 바꿔 발행
규모·안정성 장비가 많아지면 클러스터 브로커(EMQX, HiveMQ) 또는 클라우드 IoT 서비스
감시 브로커 접속 수, 메시지량, 끊긴 장비(Last Will)를 대시보드로 확인

과정에 넣는다면

  • Stage 1 첫 실습: 1~2단계(브로커 띄우기, 가짜 센서, 저장기).
  • Stage 1 후반: 3단계(언리얼에서 펌프 색 바꾸기).
  • Stage 2 이후·캡스톤: 4단계(토픽 설계서, 보안, 장비 수를 늘린 부하 시험).

인터뷰에서는 "MQTT를 띄우는 건 브로커 설치 몇 분, 코드 열 줄 수준이다. 실무 역량은 토픽 설계, 데이터 약속, 보안, 저장, 규모에서 갈리고, 과정은 이 순서로 난이도를 올린다"라고 말할 수 있다.

인터뷰용 한 문단

"MQTT는 IoT 표준 메시지 프로토콜입니다. 센서가 토픽이라는 주소로 데이터를 발행하면, 브로커가 그 토픽을 구독한 언리얼과 저장 서버에 동시에 전달합니다. 가볍고 끊김에 강해서 항만이나 공장 현장 데이터 수집에 널리 쓰이고, 삼우이머션의 부산항 터미널 디지털트윈도 MQTT로 실시간 데이터를 받았습니다. 다만 MQTT는 전달만 하기 때문에, 이력 저장, 정제, 분석은 그 뒤의 빅데이터 파이프라인에서 처리합니다. 우리 과정은 첫 단계에서 MQTT로 센서 하나를 언리얼에 연결하는 것부터 시작합니다."
