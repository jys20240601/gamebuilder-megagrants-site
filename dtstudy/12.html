샘플 코드가 실무에서 바뀌는 다섯 가지

샘플 코드는 11_정제정합_샘플코드.md 참고. 아래 예시 코드는 모두 2026-11-16에 실제로 돌려 본 결과를 함께 적었다(pandas 3.1, pyproj 3.8).

한눈에

샘플 실무 바꾸는 이유
1 장비 대장을 코드 안에 DB 표나 설정 파일 장비가 수백 대, 코드 수정 없이 현장 담당자가 고치고, 여러 프로그램이 같이 씀
2 SQLite TimescaleDB, InfluxDB 하루 수천만 건, 여러 프로그램이 동시에 쓰고 읽음, 시간 집계·보관 정책
3 직전 값과 비교 이동 중앙값, 통계 기준 노이즈 많은 센서의 오탐, 천천히 변하는 이상
4 좌표 근사식 pyproj, 언리얼 Georeferencing 지도·도면 좌표계와 정확히 맞추기
5 메시지 하나씩 pandas 묶음 처리, Kafka 스트림 대량을 빠르게, 놓치지 않고, 여러 곳에 나눠 처리

1. 장비 대장: 코드 안의 표 → DB 표나 설정 파일

샘플에서는 장비 대장이 파이썬 코드 안에 들어 있다. 장비가 3대일 때는 괜찮지만, 실무에서는 문제가 생긴다.

  • 장비가 수백~수천 대다.
  • 장비를 추가하거나 정상 범위를 바꿀 때마다 개발자가 코드를 고치고 다시 배포해야 한다.
  • 저장기, 알람, 언리얼, 대시보드가 같은 대장을 봐야 하는데 코드 안에 있으면 나눠 쓸 수 없다.
  • 누가 언제 무엇을 바꿨는지 기록이 남지 않는다.

설정 파일로 빼면 개발자가 아니어도 고칠 수 있다. 엑셀로 관리하고 CSV로 내보내는 경우가 많다.

asset_id,actor,kind,unit,vmin,vmax,max_jump,calibrated
pump03,BP_Pump_03,temp,C,-20,120,5,2026-10-01
pump05,BP_Pump_05,temp,F,-20,120,5,2026-09-15
crane07,BP_Crane_07,position,deg,,,5,

DB 표로 두면 여러 프로그램이 동시에 읽고, 관리 화면에서 고치고, 변경 이력을 남길 수 있다.

CREATE TABLE assets (
  asset_id   TEXT PRIMARY KEY,   -- 센서 ID
  actor      TEXT,               -- 언리얼 액터 이름
  kind       TEXT,               -- temp, position ...
  unit       TEXT,               -- 센서가 보내는 단위
  vmin REAL, vmax REAL,          -- 정상 범위
  max_jump   REAL,               -- 허용 변화량
  calibrated DATE                -- 마지막 교정일
);
  • 저장기는 시작할 때와 일정 간격마다 이 표를 읽는다.
  • 언리얼은 같은 내용을 Data Table로 가져와 액터와 연결한다.
  • 현업에서는 이것을 마스터 데이터 또는 자산 대장이라고 부르고, 설비 관리 시스템(CMMS·EAM)에 이미 있는 경우가 많아 그쪽과 연동한다.

2. DB: SQLite → TimescaleDB나 InfluxDB

DB 무엇 맞는 곳
SQLite 파일 하나짜리 DB. 설치가 필요 없고 파이썬에 들어 있다 실습, 작은 도구, 기기 안 임시 저장. 여러 프로그램이 동시에 많이 쓰면 약하다
TimescaleDB 널리 쓰는 PostgreSQL DB에 시계열 기능을 더한 확장 SQL을 그대로 쓰고, 장비 대장 같은 일반 표와 센서 시계열을 한 DB에서 조인해야 할 때
InfluxDB 처음부터 시계열 전용으로 만든 DB 센서 수집·모니터링 위주로 간단하게 시작할 때. Telegraf로 코드 없이 MQTT → DB 연결

TimescaleDB가 해 주는 것

  • 표를 시간 단위로 자동으로 잘게 나눠 저장한다(하이퍼테이블). 오래된 구간은 압축한다.
  • time_bucket('1 minute', time)으로 1분·1시간 집계를 바로 낸다.
  • 1분 평균 같은 집계를 미리 계산해 두는 기능(연속 집계), "원값은 30일만 보관" 같은 보존 정책을 설정으로 건다.

InfluxDB의 데이터 모양: 표 이름(measurement), 검색용 꼬리표(tag), 값(field), 시각을 한 줄로 적는다.

temp,asset_id=pump03,quality=ok value=32.1 1794704400000000000

맨 뒤 숫자는 2026-11-15 01:00:00 UTC를 나노초로 적은 시각이다. 조회 언어는 버전에 따라 InfluxQL, Flux, SQL로 다르다.

샘플에서 바꿀 곳: sqlite3.connect(...)를 PostgreSQL 연결(psycopg 등)로 바꾸면 INSERT 문은 거의 그대로 쓴다. 대시보드(Grafana)는 두 DB 모두 바로 붙는다.

3. 튀는 값 판정: 직전 값 비교 → 이동 중앙값, 통계 기준

직전 값과 비교하는 방식의 한계

  • 원래 흔들림(노이즈)이 큰 센서는 정상인데도 튀는 값으로 잡힌다(오탐).
  • 하루에 조금씩 오르는 이상은 매번 차이가 작아서 못 잡는다(미탐).
  • 센서마다 "몇 도 이상이면 튄다"를 사람이 정해야 한다.

이동 중앙값 (+ MAD 기준, 햄펠 필터)

최근 몇 개 값의 중앙값을 기준으로 삼는다. 중앙값은 한두 개가 크게 튀어도 거의 변하지 않아서 기준이 안정적이다. 얼마나 멀어야 튀는 값인지는 그 구간의 평소 흔들림 폭(MAD, 중앙값으로부터의 거리의 중앙값)의 몇 배로 정한다.

from statistics import median

def hampel(values, window=5, k=3.0):
    """최근 window개의 중앙값에서 k×MAD보다 멀면 spike로 표시한다."""
    flags = []
    for i, v in enumerate(values):
        recent = values[max(0, i - window + 1): i + 1]
        med = median(recent)
        mad = median(abs(x - med) for x in recent) or 0.1   # 0이면 최소폭
        flags.append("spike" if abs(v - med) > k * 1.4826 * mad else "ok")
    return flags

temps = [32.1, 32.3, 32.2, 85.0, 32.4, 32.2, 32.5, 32.3]
print(list(zip(temps, hampel(temps))))
# → 85.0만 spike, 나머지는 모두 ok

통계 기준 (평균 ± 3 표준편차, z점수)

평소 데이터의 평균과 표준편차를 구해 두고, 새 값이 평균에서 표준편차의 몇 배 떨어졌는지(z점수) 본다. 보통 3배를 넘으면 이상으로 본다.

from statistics import mean, stdev
base = [32.1, 32.3, 32.2, 32.4, 32.2, 32.5, 32.3, 32.0, 32.6, 32.1]   # 평소 값
mu, sd = mean(base), stdev(base)
for v in (32.4, 33.5, 85.0):
    z = (v - mu) / sd
    print(v, round(z, 1), "spike" if abs(z) > 3 else "ok")
# → 32.4 z=0.7 ok / 33.5 z=6.5 spike / 85.0 z=279.2 spike
  • 33.5℃는 직전 값과 1℃ 남짓 차이라 샘플 방식(5℃ 기준)으로는 못 잡지만, 평소 흔들림이 아주 작은 센서라 통계 기준으로는 이상이다.
  • 실무에서는 "같은 요일·같은 시간대의 평소 값"처럼 기준 구간을 잘 고르는 것이 중요하다(낮과 밤의 정상값이 다르다).
  • 더 나아가면 여러 센서를 함께 보는 이상탐지 모델(머신러닝)을 쓴다. 이때도 판정은 지우지 않고 표시한다.

4. 좌표 변환: 근사식 → pyproj, 언리얼 Georeferencing

샘플의 근사식은 원점 주변을 평평하다고 보고 진북 기준 동·북 거리를 계산한다. 좁은 현장에서는 쓸 만하지만, 다른 데이터와 섞으면 어긋난다.

pyproj는 좌표계 변환 표준 라이브러리(PROJ)의 파이썬 판이다. EPSG 번호만 주면 정확히 바꾼다.

from pyproj import Transformer
to5186 = Transformer.from_crs("EPSG:4326", "EPSG:5186", always_xy=True)  # 입력은 경도, 위도 순서
ox, oy = to5186.transform(129.08000, 35.10500)   # 터미널 원점
cx, cy = to5186.transform(129.08200, 35.10560)   # 크레인
print(cx - ox, cy - oy)
# → 원점 5186 = (389650.74, 280723.92), 크레인 = (389831.73, 280794.31)
# → 원점 기준 동 180.99m, 북 70.39m

같은 크레인인데 결과가 다르다.

방법 동 북
샘플 근사식(진북 기준) 182.34m 66.57m
pyproj EPSG:5186(국내 지도 좌표) 180.99m 70.39m
  • 차이는 북쪽으로 약 3.8m다. EPSG:5186은 동경 127°를 기준으로 한 평면 지도 좌표라서, 부산(동경 129°)에서는 지도의 북쪽이 진북과 약 1.2° 틀어져 있고 거리도 0.04% 정도 늘어난다.
  • 터미널 3D 모델이 국내 지도·도면(EPSG:5186)으로 만들어졌는데 GPS를 근사식으로 바꾸면, 화면 속 크레인이 실제보다 몇 m 어긋난 곳에 서게 된다.
  • 그래서 실무에서는 기준 좌표계를 하나로 정하고(예: 5186), 센서·지도·도면을 모두 그 좌표계로 맞춘다.

언리얼 Georeferencing

  • 언리얼 공식 플러그인이다. 레벨에 GeoReferencingSystem 액터를 두고 원점의 위경도와 쓸 좌표계(EPSG 번호)를 지정한다.
  • 블루프린트에서 위경도를 엔진 좌표로 바꾸는 노드(Geographic To Engine 등)를 쓰면, 서버가 보낸 위경도를 언리얼이 직접 바꾼다.
  • 지구 규모로 다룰 때는 Cesium for Unreal의 CesiumGeoreference가 같은 일을 한다.

어디서 바꿀까: DB에는 원래 의미가 살아 있는 위경도를 저장하고, 화면에 그릴 때 언리얼(또는 서버의 pyproj)이 바꾸는 방식이 흔하다. 어느 쪽이든 한 곳에서 같은 좌표계 규칙으로 바꿔야 한다.

5. 처리 방식: 메시지 하나씩 → pandas 묶음 처리, Kafka 스트림

샘플처럼 하나씩 처리하면 단순하고 바로 반응하지만, 실무에서는 한계가 있다.

  • 하루 수천만 건이면 느리다.
  • 저장기 프로그램이 멈춘 동안 온 메시지는 놓친다.
  • 정제, 알람, 저장, AI 분석처럼 여러 프로그램이 같은 데이터를 써야 할 때 나누기 어렵다.

pandas 묶음 처리(배치): 1시간치·하루치를 표로 한꺼번에 처리한다. 한 줄씩 반복하지 않고 열 전체를 한 번에 계산해서 빠르다. 탐색, 재정제, 보고서, 모델 학습 데이터 만들기에 쓴다. 더 빠른 대안으로 Polars가 있다.

import pandas as pd
df = pd.DataFrame({
    "time": pd.date_range("2026-11-15 01:00:00", periods=12, freq="200ms", tz="UTC"),  # 1초 5회
    "asset_id": "crane07",
    "east_m": [182.3, 182.5, 182.8, 183.0, 250.0, 183.5, 183.7, 184.0, 184.2, 184.5, 184.7, 185.0],
})
df["med5"] = df["east_m"].rolling(5, min_periods=1).median()        # 이동 중앙값
df["quality"] = (df["east_m"] - df["med5"]).abs().gt(5).map({True: "spike", False: "ok"})
per_sec = df[df["quality"] == "ok"].set_index("time")["east_m"].resample("1s").last()   # 1초 칸
# → 250.0 하나만 spike
# → 1초 칸: 01:00:00 183.0 / 01:00:01 184.5 / 01:00:02 185.0

Kafka 스트림 처리: 서버 안에서 대용량 메시지를 보관하면서 나눠 주는 플랫폼이다.

센서 → MQTT 브로커 → (연결기) → Kafka ─┬→ 정제 서비스 → 시계열 DB
                                      ├→ 알람 서비스 → 알람 앱
                                      ├→ AI 분석 서비스
                                      └→ 언리얼 실시간 화면
  • Kafka는 메시지를 디스크에 일정 기간 보관한다. 처리 프로그램이 멈췄다 다시 켜져도 읽던 자리부터 이어 읽는다. 규칙을 바꾸면 지난 데이터를 처음부터 다시 처리할 수도 있다.
  • 같은 데이터를 여러 서비스가 각자 읽는다. 데이터가 많으면 파티션으로 나눠 여러 대가 함께 처리한다.
  • "1분 평균이 기준을 넘으면 알람" 같은 실시간 계산은 Flink, Kafka Streams 같은 스트림 처리 엔진이 맡는다.
  • MQTT와 Kafka의 역할 차이: MQTT는 현장의 많은 기기와 가볍게 주고받는 데, Kafka는 서버 안에서 대용량을 보관·분배하는 데 쓴다. 둘은 경쟁이 아니라 앞뒤로 이어 쓴다.

언제 Kafka까지 필요한가: 장비 수천 대, 처리 프로그램이 여럿, 재처리가 필요한 경우다. 장비 수십~수백 대 규모는 MQTT + 저장기 + 시계열 DB로 충분한 경우가 많다. 교육 과정에서는 개념과 작은 실습으로 다루고, 캡스톤 규모에 맞춰 고르는 것이 현실적이다.

인터뷰용 한 문단

"실습은 SQLite와 메시지 단위 처리로 원리를 익히고, 실무 수준으로는 장비 대장을 DB로 분리하고, TimescaleDB나 InfluxDB 같은 시계열 DB에 저장하고, 이동 중앙값·통계 기준으로 이상값을 표시하고, pyproj나 언리얼 Georeferencing으로 지도 좌표계와 정확히 맞추고, 대량 데이터는 pandas 배치나 Kafka 스트림으로 처리하도록 단계적으로 확장합니다. 예를 들어 같은 크레인 위치도 근사식과 국내 표준 좌표(EPSG:5186)로 바꾼 결과가 4m 가까이 다르기 때문에, 기준 좌표계를 하나로 정하는 것부터 가르칩니다."
